# Nexora - Accounting Event Ledger Design (S2.1)

- Status: `active` (design), build `not started`
- Last updated: 2026-08-06
- Source: Stage 6 Finance Core Platform request, logged as `accepted-improvements.md` I-020
- Segment: `segments/S2.1-accounting-event-ledger.md`
- Architecture: `architecture.md` C7, ADR-5

This is the design depth behind S2.1's compact segment spec — not a
replacement for it. Code is not generated here (design/documentation only,
per the 2026-08-06 decision); it applies when S2.1 is actually built, after
S1.3/S1.4 close per the locked Phase 1-before-Phase-2 dependency.

## Business analysis

Every module that will eventually post to the books (procurement, inventory,
sales, HR/payroll, manufacturing, projects) must never write directly to a
journal or account balance. Instead it submits an `AccountingEvent` — a
statement of "this business thing happened," not "post this to account X."
This is what lets business modules stay financially dumb (S3.x doesn't need
to know chart-of-accounts structure) while S2.2 owns all posting logic
centrally. This is `architecture.md`'s own stated design ("Finance is the
first deep business domain and receives posted accounting events from
adjacent modules through a controlled event ledger"), not a new decision.

## Functional requirements

| ID | Requirement |
|---|---|
| FR-EL-1 | Any module can submit an `AccountingEvent` with an `Idempotency-Key`; duplicate submission produces zero duplicate side effects (already S2.1's locked NFR). |
| FR-EL-2 | Events are typed (`event_type`, e.g. `sales.invoice.issued`, `procurement.receipt.posted`) with a JSON payload validated against a per-type registered schema — the type registry is extensible so new modules register new event types without changing this segment's code. |
| FR-EL-3 | Events move through one-directional states: `received -> validated -> posted \| rejected`, or `received -> validated -> failed -> retry -> posted \| dead`, with a bounded retry count. |
| FR-EL-4 | Posted events are immutable; corrections use compensating events, never mutation — already S2.1's locked acceptance criterion. |
| FR-EL-5 | Every event carries `source_type`/`source_id` so a journal line can always be traced back to the exact originating business document. |

## Business / posting rules

- `payload_hash` is computed over the canonicalized `payload_json` plus
  `idempotency_key`, so a byte-identical resubmission is caught even if the
  idempotency key itself is regenerated by a retrying caller.
- S2.1 validates and stores; it does **not** decide account codes or amounts
  — that logic lives entirely in S2.2. This keeps the intake layer stable
  even as posting rules evolve.
- Cross-module writes happen only through this event submission — never
  direct table mutation — per `architecture.md`'s data-ownership rule.

## Database schema (elaborates the locked `AccountingEvent` entity)

| Field | Type | Notes |
|---|---|---|
| `id` | uuid | primary key |
| `tenant_id` | uuid | required, indexed with `idempotency_key` (unique composite) |
| `source_type` | text | e.g. `sales_invoice`, `stock_adjustment` |
| `source_id` | uuid | soft reference — no cross-module FK, per architecture's ownership rule |
| `event_type` | text | validated against the type registry |
| `payload_json` | jsonb | validated against the type's registered schema |
| `payload_hash` | text | sha-256 of canonicalized payload + idempotency key |
| `idempotency_key` | text | required, unique per tenant |
| `state` | enum | `received, validated, posted, rejected, failed, retry, dead` |
| `retry_count` | int | default 0 |
| `created_at` / `posted_at` | timestamptz | UTC, injected clock for testability (same pattern as S1.3's SLA timestamps) |
| `audit_ref` | uuid | link to the `AuditEvent` recording this event's lifecycle |

## API contracts

| Route | Method | Notes |
|---|---|---|
| `/api/v1/finance/accounting-events` | POST | Idempotent (Idempotency-Key header), returns 201 or the original result on replay |
| `/api/v1/finance/accounting-events/{id}` | GET | Permission `finance.accounting_event.read` |
| `/api/v1/finance/accounting-events` | GET | Cursor-paginated (`{items, next_cursor}`), filterable by `state`, `event_type`, `source_type` |

## Validation rules

`event_type` must exist in the registered type registry; `payload_json` must
validate against that type's schema; `source_type` must be a known module
identifier. Unknown type or schema-invalid payload is rejected at intake
(`state = rejected`), never silently accepted.

## Security model / permissions

Reuses S1.2's authorization model exactly — no new mechanism. Write access
(`finance.accounting_event.create`) is granted to service identities of
other modules (future signed service-identity adapter, tracked as a Q-003
follow-on, not a new open decision). Read access is scoped to finance and
audit roles. Tenant isolation is enforced identically to every other S1.2
resource (repository-filtered plus tenant-composite constraints).

## Reports / dashboards

An event-intake dashboard (received/posted/failed/dead counts, retry queue
depth, oldest unprocessed event age) — this feeds S2.3's operational
dashboards, not a separate reporting surface.

## Audit requirements

Every state transition emits an `AuditEvent` (reusing S1.2's hash-chained,
append-only writer) with before/after state and correlation id — no new
audit mechanism is introduced.

## Performance considerations

Idempotency check is O(1): unique index on `(tenant_id, idempotency_key)`.
The event table is effectively append-only pre-posting (only `state` and
`retry_count` mutate), so write contention stays low even under high event
volume.

## Error handling

Canonical `{code, message, details, correlation_id}` shape, reused as-is.
Codes: `FINANCE_EVENT_SCHEMA_INVALID`, `FINANCE_EVENT_UNKNOWN_TYPE`,
`FINANCE_EVENT_DUPLICATE` (idempotent replay returns the original result,
not an error — consistent with the already-locked idempotency convention).

## Integration points

Every future business-module segment (S3.1 procurement/inventory, S3.2
sales/HR/projects, S3.3 manufacturing) is a producer. S2.2 is the sole
consumer that turns posted events into journal entries.

## Testing strategy

Reuses `verification-matrix.md`'s levels (unit, integration, contract,
security, migration — matching S2.1's own locked verify command). Specific
cases: duplicate idempotency-key rejection, payload-hash collision on a
regenerated key, schema validation per registered event type, retry-to-dead
path after the bound is exceeded, cross-tenant event isolation.
