# S1.2 Security Baseline Research

- Researched: 2026-07-29
- Scope: tenant-scoped identity mapping, role/attribute authorization,
  separation of duties, append-only audit evidence, and reversible local
  persistence.
- Source policy: primary standards/guidance and official runtime/database
  documentation.

## Findings

| Design claim | Primary evidence | Applied decision |
|--------------|------------------|------------------|
| Protected access must deny by default and validate permission on every request. | [OWASP Authorization Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Authorization_Cheat_Sheet.html), reviewed 2026-07-29; [OWASP ASVS](https://owasp.org/www-project-application-security-verification-standard/), reviewed 2026-07-29; [NIST RBAC FAQ](https://csrc.nist.gov/Projects/role-based-access-control/faqs), updated 2026-03-04. | Routes carry an explicit permission. The application default authorizer rejects all. Authentication alone never grants access. |
| ERP authorization needs roles plus tenant, record, field, and operation attributes. | [NIST RBAC FAQ](https://csrc.nist.gov/Projects/role-based-access-control/faqs), reviewed 2026-07-29; [NIST SP 800-162 ABAC guide](https://csrc.nist.gov/pubs/sp/800/162/upd2/final), reviewed 2026-07-29; [OWASP Authorization Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Authorization_Cheat_Sheet.html), reviewed 2026-07-29. | User-role and role-permission relations are explicit. The evaluator also checks tenant equality, policy scope, requested fields, record ownership/company attributes, and access-time constraints. |
| Separation of duties requires both assignment-time role conflicts and access-time transaction constraints. | [NIST RBAC FAQ](https://csrc.nist.gov/Projects/role-based-access-control/faqs), reviewed 2026-07-29; [NIST SoD glossary](https://csrc.nist.gov/glossary/term/separation_of_duty), reviewed 2026-07-29; [NIST mutual-exclusion paper](https://www.nist.gov/publications/mutual-exclusion-roles-means-implementing-separation-duty-role-based-access-control), reviewed 2026-07-29. | Assignment rejects mutually conflicting roles. Authorization denies self-approval and other configured distinct-actor violations even when the role has the action permission. |
| Audit evidence needs attributable event context and protection from unauthorized modification/deletion. | [NIST SP 800-53 Rev. 5 update 1](https://csrc.nist.gov/pubs/sp/800/53/r5/upd1/final), reviewed 2026-07-29; [NIST SP 800-92](https://csrc.nist.gov/pubs/sp/800/92/final), reviewed 2026-07-29; [OWASP Logging Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Logging_Cheat_Sheet.html), reviewed 2026-07-29. | Audit records include actor, tenant, action, target, correlation, source, approval context, timestamp, and before/after hashes. The repository exposes append/read only, and database triggers reject update/delete. Tokens, secrets, bodies, and raw before/after values are excluded. |
| Persistence must use explicit transactions, enforced foreign keys, and database-enforced immutability. | [PostgreSQL constraint documentation](https://www.postgresql.org/docs/current/ddl-constraints.html), reviewed 2026-09-28; [PostgreSQL trigger documentation](https://www.postgresql.org/docs/current/triggers.html), reviewed 2026-09-28; [Psycopg transaction documentation](https://www.psycopg.org/psycopg3/docs/basic/transactions.html), reviewed 2026-09-28. | S1.2 uses PostgreSQL through Psycopg with parameterized statements, explicit transaction boundaries, foreign-key constraints, and rejecting audit triggers. Rollback is allowed only while security/audit tables are empty. |

## Contradictions and limitations

- The locked architecture selects managed OIDC/SAML authentication plus a
  Nexora-owned authorization layer. No identity provider, issuer, audience,
  signing-key source, or session policy is selected yet. S1.2 therefore ships
  a trusted-claims-provider boundary and tenant-aware account mapping, not a
  home-grown token validator.
- PostgreSQL is the only persistence implementation. Local execution does not
  by itself prove encryption at rest, high availability, centralized audit
  archive, retention enforcement, or production-scale concurrency.
- Database triggers make records append-only to ordinary SQL clients using
  this schema. They do not by themselves make a privileged database operator,
  backup, or storage layer tamper-proof. Production must add restricted writer
  credentials, centralized protected storage, monitoring, backup, and
  retention controls.
- Psycopg is a runtime dependency and must remain covered by dependency and
  vulnerability scanning.

## Result

The researched design is compatible with `architecture.md` C2/C10 and R13.1:
managed authentication remains an integration boundary, while Nexora owns a
deny-by-default role-and-attribute policy evaluator and append-only audit
evidence model. The implementation must prove allowed, denied, cross-tenant,
field, record-scope, static/dynamic SoD, audit-failure, immutability, forward
migration, clean rollback, and rollback-preservation paths.
