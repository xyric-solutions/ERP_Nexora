# S1.3 Tenant and Workflow Foundation Research

- Researched: 2026-07-29
- Scope: tenant configuration validation, fiscal-period integrity, supported
  currencies/modules, acyclic approval definitions, approval authorization,
  SLA timestamps, and controlled-action audit evidence.
- Source policy: locked Nexora intent plus primary standards/guidance and
  official Python/database documentation.

## Contradictions and limitations

- The active repository has no browser/mobile client. S1.3 therefore chooses
  the PRD's admin API option. WCAG/browser execution is not applicable to this
  backend-only batch; structured field errors and draft recovery are verified
  directly. No accessibility pass is claimed.
- ISO 4217 is maintained and its code data can change. This dependency-free
  reference does not embed an allegedly exhaustive static list; deployment
  must provide a reviewed catalog adapter.
- PostgreSQL row locking and transaction boundaries keep overlap checks and
  inserts within one concurrency-safe write boundary.
- Local PostgreSQL execution is not proof of production encryption, HA,
  retention, backup, or operator-proof audit evidence; those remain Q-004
  deployment controls.
- Notifications and a visual workflow builder are C4/C12 surfaces for later
  segments. S1.3 stores metadata and exposes deterministic threshold, SLA,
  exception, and human-approval behavior without introducing those transports.

## Result

The design is compatible with C3/C4 and R1.1: tenant setup uses typed,
tenant-owned records and recoverable drafts; workflow definitions are
versioned and acyclic; approval instances preserve source/version/audit
references; and all material setup/approval actions reuse S1.2 authorization
and audit controls. Direct gates must cover duplicates, overlap, inactive and
cross-tenant references, unsupported catalog values, cycles, threshold
routing, SLA status, exception routing, self-approval denial, audit failure,
migration rollback, API draft recovery, and a local command-latency sample.
