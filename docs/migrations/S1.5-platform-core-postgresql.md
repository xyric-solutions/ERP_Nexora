# S1.5 Platform Core PostgreSQL Migration

## Scope

The ordered production migration set contains:

- `0001_platform_core`: tenant/company hierarchy, fiscal calendars,
  accounting periods, currencies/rates, modules, policies, numbering
  sequences, and setup drafts.
- `0002_platform_admin_controls`: durable command idempotency and immutable,
  tenant-chained Platform administration audit evidence.
- `0003_localization_foundation`: country/jurisdiction and legal-entity reference
  catalogs, immutable versioned localization-pack metadata, effective-dated
  company legal/payroll configuration, and explicit legacy/new-company
  localization controls. It seeds no country-specific statutory rules.

The set owns the production Platform schema. Development and Demo use their
PostgreSQL migration chain and apply the corresponding globally numbered
`0016_localization_foundation` migration without country-specific rule data.

## Apply and inspect

The application migrator uses Psycopg 3 and a dedicated autocommit connection,
then applies every missing ordered version inside one explicit, advisory-locked
transaction:

```python
from app.platform.postgres import apply_platform_core

apply_platform_core(os.environ["NEXORA_DATABASE_DSN"])
```

The database role applying migrations must own the schema. Runtime application
roles must be non-owner, non-superuser, must not have `BYPASSRLS`, and receive
only the table privileges required by their deployment profile.

## Tenant context

Every request or command transaction must set its trusted tenant context before
tenant-owned queries:

```sql
SELECT set_config('nexora.tenant_id', $1, true);
```

The final `true` makes the setting transaction-local so it cannot leak through
a pooled connection. Missing context is default-deny under the forced row-level
security policies. The authenticated and authorized server boundary decides the
tenant value; client-supplied IDs are never trusted directly.

## Rollback

`rollback_platform_core()` succeeds only while all Platform Core business,
localization, and control-evidence tables are empty. If tenant/configuration,
pack metadata, company localization state, idempotency, or audit data exists,
the rollback raises and the transaction preserves every version, schema
object, policy, and row. Data migration or archival requires a separate
reviewed plan; the rollback never cascades away evidence.
Because `FORCE ROW LEVEL SECURITY` also applies to a non-superuser table owner,
the rollback transaction temporarily removes `FORCE` before inspecting rows.
Only the owning migration role can do this, and any populated-data exception
rolls those DDL changes back, leaving every RLS force flag intact.

## Verification

Run the disposable PostgreSQL gate:

```powershell
python scripts/verify_postgres_platform.py
```

The script starts an isolated `postgres:18-alpine` container on loopback, runs
the focused migration/RLS/API/idempotency/audit/concurrency suite using a
non-owner application role, and removes the container. It does not persist
credentials or database volumes.
