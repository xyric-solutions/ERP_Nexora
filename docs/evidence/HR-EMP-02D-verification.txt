HR-EMP-02D — Employee Profile, Private Data, Contacts, Emergency Contacts and Document References
Verification date: 2026-09-30
Status: CLOSED WITH WAIVERS

IMPLEMENTED
- Existing `employee` remains the canonical identity; no competing employee
  master, relationship, assignment, contact, or document authority was
  introduced. Employee profile approval does not imply active employment.
- `hr_employee_profile_version` (new) is a typed, effective-dated, append-only
  history of identity fields (name parts, work/personal email, phone, date of
  birth); `employee` remains the current-state projection consumed unchanged
  by existing Attendance/Payroll joins.
- `employee_contact` (existed as a 1-row address table) is reshaped into a
  typed, multi-row, effective-dated contact log (email/phone/address ×
  work/personal/other), with a database trigger keeping
  `employee.work_email/personal_email/phone` in sync as a read projection and
  a guard trigger blocking direct writes to those columns outside that path.
- `employee_emergency_contact` and `employee_document` (existed as static
  rows) are reshaped into append-only, effective-dated (emergency contact) and
  metadata-only, immutable (document) records respectively. Document binary
  storage/download remains unavailable by design; `storage_key` is legacy
  reference-only and never accepted or returned by 02D APIs.
- Raw `national_id` ingestion is removed from employee create/update entirely
  (Q-004 fail-closed); a new read-only `employee_sensitive_metadata` endpoint
  returns only masked bank/tax/national-identifier values plus
  `"write_status":"blocked_by_q004"`. No vault/KMS was implemented or claimed.
- The existing HR workspace gains a focused Profile tab (history, contacts,
  emergency contacts, documents, permission-gated sensitive metadata) reusing
  established Nexora UI conventions; no HR module redesign.

DATABASE AND MIGRATION
- Forward: app/hr/postgres/migrations/0013_employee_profile_satellites.forward.sql
- Rollback: app/hr/postgres/migrations/0013_employee_profile_satellites.rollback.sql
- New table `hr_employee_profile_version` with a GiST exclusion constraint
  (partial on `supersedes_version_id IS NULL`) preventing overlapping open
  segments per employee, immutable-history trigger, and forced RLS.
- `employee_contact` gains `id`, `channel`, `contact_usage`, `is_primary`,
  `status`, `effective_from/to`, provenance columns, a unique partial index on
  the current primary per channel/usage, and an immutable-history trigger.
- `employee_emergency_contact` gains `email`, `priority`, `status`,
  `effective_from/to`, `supersedes_contact_id`, provenance columns, a unique
  partial index on current priority, and an immutable-history trigger.
- `employee_document` gains `issuing_authority`, `verification_status`,
  `notes`, `status`, `supersedes_document_id`, provenance columns; `storage_key`
  becomes nullable; mutation is rejected outright (append-only).
- Existing rows are captured as explicit `migration:0013-*`-tagged evidence
  during the forward migration (current-state snapshot), never guessed.
- Rollback refuses once any non-migration-tagged evidence exists in any of the
  four affected tables (populated-rollback protection), matching the existing
  02A-02C rollback-guard pattern.

DEFECTS FOUND AND FIXED (all confirmed by real disposable-PostgreSQL tests,
not review alone; all pre-existed in the inherited uncommitted work, none were
introduced by this session's own additions)
- `employee_action`'s "update"/"update_private" branches raised
  `UnboundLocalError` on `workflow_result` (a pre-existing defect in the
  already-closed 02A-02C code, never exercised by 02C's own test suite; newly
  reachable because 02D wires profile-version history into this exact path).
  Fixed by initializing `workflow_result = None` before the action branch
  instead of only inside the submit/approve/reject/change_status branch.
- Migration 0013's `guard_employee_contact_projection` trigger used
  `current_setting(...,true)<>'on'`, which evaluates to SQL `NULL` (not
  `TRUE`) whenever the session variable was never set — making the guard a
  silent no-op for any session that never went through the internal sync
  path, i.e. any real external write. A direct `UPDATE employee SET
  work_email=...` bypass succeeded instead of being blocked. Fixed with
  `COALESCE(current_setting(...,true),'off')<>'on'`.
- `close_contact`/`close_emergency_contact` set the closed record's
  `effective_to` to the same date the new segment starts (not the day
  before, unlike the correct pattern already used by `close_profile_version`),
  and the "as-of" list queries additionally filtered on live `status`. Combined,
  a historical `as_of` lookup for a date safely before a supersession could
  never find the record that was actually active then. Fixed by closing on
  `next_effective_from::date-1` and removing the `status='active'` filter from
  the as-of date-range clause.
- `_append_profile_version`'s same-day-revision branch intentionally never
  closes the original ("root") row, relying on `supersedes_version_id` to
  exclude later revisions from the exclusion constraint. The next
  *different-day* append closed whichever row `get_profile_version` picked as
  "current" (the highest revision), not that still-open root row, leaving an
  unbounded-forward date range that collided with the next segment —
  reproducible on the ordinary sequence "create employee -> add a contact same
  day -> make a dated change later." Fixed by adding
  `get_open_root_profile_version` and closing that row specifically.
- `tests/postgres/test_hr_foundation.py` still submitted raw `national_id` in
  its shared `_employee_payload()` fixture; updated to match the intentional
  Q-004 removal (masked identifier now asserted `None` on creation).
