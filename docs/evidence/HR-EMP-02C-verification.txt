HR-EMP-02C — Effective Assignments, Organization, Jobs, Designations and Localization Integration
Verification date: 2026-09-29 Asia/Karachi
Status: CLOSED WITH WAIVERS

IMPLEMENTED
- Existing employee_assignment is the effective operational-placement authority;
  no competing Employee, relationship, assignment, work-location or jurisdiction
  model was introduced.
- Operational segments require an effective employed/temporarily-inactive
  hr_employment_relationship for the same Employee and legal employer.
- Assignment changes close the preceding authoritative segment and append a new
  immutable segment. Explicit as_of reads reconstruct deterministic boundaries.
- Job is a separate hr_master_record type from designation and job_grade.
- employee_assignment_org_unit stores normalized business-unit, division,
  branch, department and warehouse placement against the existing arbitrary,
  acyclic organization_unit hierarchy.
- Existing branch_id and department_id remain validated compatibility
  projections. Legacy HR-01 assignment commands remain available only as
  explicit legacy_compatibility evidence; no relationship is inferred.
- Manager validation is effective-dated, legal-employer scoped, self-safe and
  cycle-safe. An operational manager must have an effective operational
  assignment in the same legal employer.
- Work location remains explicit. The existing HR-LOC resolver consumes the
  new authoritative segment; cross-country resolution stays fail-closed and
  missing/unapproved localization remains readiness evidence, never compliance.
- Existing assignment GET/POST APIs now support as_of/relationship filters,
  effective change commands and change-specific contextual RBAC.
- The existing HR workspace adds a focused Assignments tab for current/as-of
  placement, relationship selection, controlled changes, localization blockers
  and immutable history.

DATABASE AND MIGRATION
- Forward: app/hr/postgres/migrations/0012_effective_assignments.forward.sql
- Rollback: app/hr/postgres/migrations/0012_effective_assignments.rollback.sql
- employee_assignment adds employment_relationship_id, job_id,
  assignment_status, source_reference and updated_at; branch/department become
  nullable compatibility projections.
- New table: employee_assignment_org_unit.
- New/updated constraints: relationship assignment scope uniqueness; typed
  relationship/job/organization FKs; assignment status/source/reason/authority
  shape checks; authoritative-period GiST exclusion; organization-type check;
  relationship-period and effective-state validation; company ancestry,
  projection consistency, manager and immutable-history triggers.
- Indexes: relationship/effective, job/effective, company/status/effective and
  organization-unit lookup.
- employee_assignment_org_unit uses FORCE ROW LEVEL SECURITY with the existing
  transaction-local tenant context. Its history cannot be updated or deleted.
- Legacy branch/department placements are deterministically backfilled and an
  insert trigger keeps raw legacy consumers synchronized.
- Clean rollback restores the prior reason/uniqueness/exclusion/trigger shape.
  Rollback refuses once job masters, operational assignments, new statuses or
  non-legacy organization placements exist.
