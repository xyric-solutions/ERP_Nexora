Nexora Username/Password Authentication - Verification Evidence
Date: 2026-08-17

Scope
-----
Post-S2.3 extension replacing the frontend's manual bearer-token and
permission-assertion form with a real tenant/username/password login endpoint.
This does not change the next planned segment (S3.1).

Architecture preserved
----------------------
- Existing UserAccount, RolePolicy, UserRoleAssignment, protected_context,
  IdentityVerifier, and RepositoryAuthorizationService remain authoritative.
- Existing protected APIs still receive Authorization: Bearer plus
  X-Tenant-ID and traverse the same identity/authorization gates.
- StaticTokenIdentityVerifier remains available for existing explicit test/dev
  integrations; issued credential sessions are accepted through a composite
  verifier.
- Enterprise SSO remains visibly unavailable and was not faked.

New authentication boundary
---------------------------
- POST /api/v1/auth/login is a public, rate-limited JSON endpoint.
- Request: tenant_id, username, password.
- Tenant existence/status, case-insensitive tenant-scoped username, password,
  and user status are validated on the backend.
- Invalid usernames and passwords share one generic 401 denial and both use a
  PBKDF2 verification path. Invalid tenant is 404, missing fields 422, and
  inactive/disabled account 403.
- Migration 0011 adds password_credential with PBKDF2-HMAC-SHA256 verifier,
  unique 16-byte salt, iteration count, and no plaintext password column.
- Successful login loads roles/permissions from active backend role policies
  and returns an eight-hour tenant-bound HMAC-SHA256 signed bearer session.
- Issued sessions re-check active UserAccount status on every protected call.
- Login responses carry Cache-Control: no-store and Pragma: no-cache.
- Request completion logs contain route/status/correlation metadata only; no
  password, password hash, request body, or access token is logged.

- Seed verification: 9 password credentials, all stored as salted hashes.
- The password is configured in the backend demo seed and documentation, never
  embedded in the frontend. The legacy ignored token manifest remains only for
  compatibility and is not required for UI login.

Frontend
--------
- Login fields: Tenant ID, Username, Password, Sign In.
- Removed from the normal experience: bearer-token field, display-name field,
  manual permission selection, fast token injection, and credentials.json
  instructions.
- The generated OpenAPI client calls POST /api/v1/auth/login.
- The browser session stores only the returned access token, tenant, display
  label, and backend permissions in the existing tab-scoped sessionStorage.
- Invalid credentials render a safe backend message; no secrets are logged.
