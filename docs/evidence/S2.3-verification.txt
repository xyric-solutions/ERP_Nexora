Direct acceptance evidence (against segments/S2.3-finance-reporting-analytics.md)
---------------------------------------------------------------------------
1. "ReportDefinition and AnalyticsSnapshot support finance statements, KPI
   dashboards, drill-down, scheduled export policy, and freshness
   metadata."
   - app/finance/reporting_models.py: ReportDefinition (id, tenant_id,
     name, module, filters_schema, schedule, export_policy -- exactly
     architecture.md's locked C8 row, plus lifecycle fields) and
     AnalyticsSnapshot (id, tenant_id, dataset, as_of, freshness_at,
     storage_ref -- same locked-row precedent). 12 unit tests
     (tests/unit/test_reporting_models.py).

2. "Dashboards only show authorized metrics and drill down to source
   records."
   - Every ReportingService method requires an explicit permission
     (finance.report.read/drilldown/consolidate/audit_read,
     finance.report_definition.manage) via the same
     RepositorySecurityCommandGate defense-in-depth pattern as every
     prior segment -- test_dashboard_metrics_denied_without_permission,
     test_drilldown_denied_without_permission.
   - Drill-down resolves real source records (see item 7 below), not
     placeholder data.

3. "Heavy reports queue asynchronously and expose status/failure
   evidence."
   - ReportJob persists a real queued/running/completed/failed state
     machine (app/finance/reporting_models.py); request_consolidated_
     statement creates the job row (the "accepted job id" step, itself
     under 300ms) then executes synchronously before returning, since no
     background worker pool exists anywhere in this codebase (confirmed
     by a full-repository search before implementation) -- disclosed as
     a v1 limitation, not hidden. Failure evidence is real:
     test_consolidated_statement_job_records_failure_reason forces a
     genuine data-integrity failure and asserts failure_reason is
     populated and no result_snapshot_id exists.

4. "Statement reports (Trial Balance, Balance Sheet, Profit & Loss, Cash
   Flow) are built from account-type-tagged trial balance rows, with the
   Balance Sheet equation (Assets = Liabilities + Equity) holding as a
   verifiable invariant."
   - All four statements are computed from Account.type-bucketed sums
     over S2.2's posted JournalLine.base_debit/base_credit -- see
     app/finance/reporting.py's _raw_balances/_account_type_map helpers,
     used by all four report methods.
   - Balance Sheet equation: test_balance_sheet_generation and
     test_balance_sheet_equation_holds_across_periods_and_reversal (the
     latter asserts the equation across multiple periods, multiple
     accounts, and a reversal). The equation is made to hold exactly via
     a "Current Year Earnings" synthetic equity line (cumulative Revenue
     minus cumulative Expense) -- standard practice in real double-entry
     systems that defer period-close sweeps, not a fabricated number (see
     app/finance/reporting.py's module docstring, ambiguity note 4).
   - Forced-failure proof the invariant check is real, not theoretical:
     test_trial_balance_fails_loudly_on_forced_imbalance writes a single-
     sided posted line directly (bypassing PostingService, simulating a
     hypothetical future bug elsewhere) and asserts ReportUnbalanced is
     raised.

5. "Budget vs Actual joins S2.2's approved budgets against actuals and
   always recomputes fresh (never stores a stale variance)."
   - budget_vs_actual filters to status="approved" budgets only, and
     computes `actual` via a live query every call, storing nothing --
     test_budget_vs_actual_recomputes_fresh_after_new_posting posts a
     new expense between two calls and asserts the actual/variance
     changed; test_budget_vs_actual_no_approved_budget_raises proves the
     named FINANCE_REPORT_NO_APPROVED_BUDGET error path.

6. "Consolidated Statements apply S2.2's consolidation-group and
   elimination rules at generation time, queued asynchronously per the
   existing heavy-report NFR, never writing back to any subsidiary's
   books."
   - test_consolidated_statement_generation, test_elimination_rule_
     actually_eliminates_intercompany_balance (proves the rule changes
     the result by comparing against an identical group without the
     rule -- not just that a flag was accepted), and
     test_consolidation_does_not_modify_subsidiary_books (byte-for-byte
     snapshot comparison of the subsidiary's own journals before/after).

7. "Drill-down resolves the full chain: report line -> GL row -> journal
   -> source AccountingEvent -> source business document, in a bounded
   number of hops regardless of which report it started from."
   - app/finance/ledger_repository.py's new list_journal_lines_for_
     account uses the existing idx_journal_line_tenant_account index,
     bounded by `limit`, resolving each distinct journal at most once
     (not per-line). app/finance/reporting.py's drilldown() then resolves
     the AccountingEvent hop only for accounting-event-sourced journals,
     caching by event id to avoid re-fetching a shared event across
     multiple lines. test_drilldown_full_accounting_event_chain proves
     the complete chain end to end (account -> line -> journal ->
     AccountingEvent -> source business document reference);
     test_drilldown_manual_entry_chain_terminus proves a manual entry's
     chain correctly terminates without a source document, rather than
     fabricating one.

Design decisions and ambiguities resolved and reported per the
mega-prompt's "stop and clearly report" instruction
---------------------------------------------------------------------------
Full text of all seven, with reasoning, lives in app/finance/reporting.py's
module docstring (not duplicated here in full) -- summary:
1. Route naming: the design doc's proposed routes violate the locked
   REST_PATH contract regex; resolved with flat snake_case nouns, same
   precedent as S2.1/S2.2's own route renames.
2. Async heavy-report execution: no worker infrastructure exists in this
   codebase; ReportJob's state machine is real, but execution is
   synchronous-in-request in this version -- disclosed, not hidden.
3. Statement sub-classification: S2.2's 5 locked account types can't
   support Cost of Sales/OpEx or Operating/Investing/Financing splits;
   the API responses carry an explicit classification_note field.
4. Balance Sheet equation without a period-close sweep: resolved via the
   standard "Current Year Earnings" synthetic equity line every real
   double-entry system uses -- an exact identity, not a fabricated number.
5. Consolidated Statements resolve an exact named ConsolidationGroup
   version id; no lineage/effective-date auto-resolution (no lineage key
   exists in S2.2's locked schema).
6. "Organization-level restriction" is real data-boundary validation
   (unknown/foreign company_id returns empty, never a cross-company leak),
   not a second RBAC dimension S1.2 doesn't have.
7. intercompany_profit elimination rules are accepted and reported as
   unapplied_rules, not silently faked (no profit-in-inventory data is
   modeled anywhere in S2.2).

Security self-review (mega-prompt's explicit review section)
---------------------------------------------------------------------------
- Authorization: every ReportingService command requires an explicit
  permission at both conceptual layers this codebase uses (HTTP-layer
  AuthorizationService plus the internal RepositorySecurityCommandGate) --
  same defense-in-depth pattern as every prior segment.
- Tenant isolation: every repository query is tenant_id-scoped;
  test_cross_tenant_isolation_period_from_other_tenant_not_found proves a
  period id from one tenant is invisible to another, not silently
  substituted.

  drill-down, dashboard, export, or async job result either -- each has
  its own permission check (finance.report.drilldown, finance.report.read,
  finance.report.consolidate), not one shared gate that would make a
  narrower grant meaningless.

  request data into any query, including the new list_journal_lines_for_
  account and date-range filters.
- No third-party Python dependency introduced backend-side; no new
  frontend dependency introduced.
